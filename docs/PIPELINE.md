# citiusdata harvest pipeline

_Generated by `ops/scripts/pipeline_guide.py` from `docs/pipeline.json`, using runs up to 24 Nov 2026, 2:05pm (Sydney time). Do not edit by hand, except the notes section: rerun the generator._

What the daily athletics harvest does on GitHub Actions, in order, and how long each part takes: from asking World Athletics which recent meets have results we do not hold, to the fetched results waiting in the pending-harvest release. It stages results only. It never adds them to championship_results.rds, the corpus or the catalogue; that stays a deliberate step done by hand. Only the daily harvest is listed. meet-forecast.yml is left out because its last successful run was on 7 Sep 2026; daily-freshness.yml is a monitor.

## Daily harvest

Workflow: [`daily-harvest.yml`](https://github.com/peteowen1/citiusdata/blob/HEAD/.github/workflows/daily-harvest.yml). Median wall time **5 min 44 s** (range 4 min 20 s to 7 min 04 s), from the first job starting to the last job ending, over the 5 run(s) listed below.

One job, once a day. It finds every meet on the World Athletics calendar (last 21 days) that has results and is not already in our corpus or catalogue, fetches each one, and uploads the raw results to the pending-harvest release. How long it takes depends mostly on how many meets are pending that day (37 in the 24 Nov run) and on the upload. Only scheduled runs are counted.

**What starts it, and what it starts:** GitHub's own schedule, 17:00 UTC (4am Sydney in summer); GitHub's cron is best-effort, so recent runs have started between about 7:30am and 2pm Sydney, 4 to 10 hours late. It can also be started by hand, naming meets to force and choosing whether to upload. Nothing reads what it publishes automatically.

## How to regenerate

```
python C:/dev/ops/scripts/pipeline_guide.py build --repo-dir <this repo>
```

It reads `docs/pipeline.json` (which workflows and jobs are the pipeline, one line per step) and the latest successful runs through `gh`, saves every response raw, and rewrites this file and `docs/pipeline-summary.json`. It fails if the config names a job, step or log pattern that no longer appears, so a renamed step cannot leave a stale description behind. Steps marked **(not confirmed)** were not checked against the script they run.
